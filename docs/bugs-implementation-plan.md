# Work: implementation plan for docs/bugs.md

Status: implemented and verified (2026-10-05). Source of requirements: [bugs.md](bugs.md). This document supersedes conflicting interaction, document, application and compiler decisions in [work-ui-latex-plan.md](work-ui-latex-plan.md). The implementation includes the native Pi compiler, protected tunnel route, and scoped local Colima cleanup described below.

## Intended result

Work should feel like one editable workspace: hold a section button for one second to edit, type directly into content, drag to arrange it, and let autosave handle persistence. Ordinary browsing stays uncluttered. Learn and Interviews share a capable freeform editor. Applications have one understandable process/status model. Résumés and letters are generated exclusively from their LaTeX sources; arbitrary uploads belong in Other documents. Heavy compilation runs on the existing Raspberry Pi through the existing Cloudflare Tunnel.

## Verified starting point

- `src/lib/edit-mode.tsx` currently saves editing sections in session storage, explaining why edit mode survives navigation.
- `src/features/content/ContentPanel.tsx`, Learn and Interviews use separate resource/note cards, modal editors and up/down controls. Replace this foundation rather than styling each old editor independently.
- `shared/applications.ts` currently separates seven broad statuses from five recruitment-step states. Applications also open separate process/appointment dialogs. This requires a coordinated model/API/UI change, not just new labels.
- `shared/model.ts` already contains `displayName`; Settings does not save it. Reuse this preference rather than change the GitHub login identity.
- The LeetCode response already contains `profile.userAvatar`. The sibling reference is `../Personal-website/src/components/LeetCodeStats.tsx` and its hooks/metrics helpers.
- Native source revisions, variants, compilation jobs, generated attachments and submitted snapshots already exist. Preserve their ownership, conflict and retention guarantees.
- SSH verification confirmed `/home/manav/base/work_project` on the Pi. It runs **aarch64 Debian 13**, has approximately **4 GB RAM** and **19 GB free disk**. Native TeX Live, `latexmk`, Poppler tools, `bwrap`, and a separate Node 22 runtime are installed; `work-compiler.service` is active and its smoke test produced a real PDF while denying a sentinel outside the sandbox.

## 1. Shared interface and editing rules

**Colour and containers.** Change shared in-page tab selection to the site's deep blue, with readable text in both themes. Keep the sidebar's distinct selected colour and the existing pink/lime/aqua content palette. Remove decorative thick coloured top strips: use ordinary ink borders/shadows, or colour the entire card when justified. A completed recruitment step uses a thin green border on every side. Audit Home, Interviews, Direction and document previews together.

**Transient edit mode.** Replace the stored set of editing routes with an active edit session. Leaving a top-level page or changing its internal content tab ends the session; returning, reloading and browser Back start in view mode. Modal/picker use and non-navigation query updates should not unexpectedly exit editing. Preserve the one-second hold, delayed fill feedback, keyboard hold and click suppression. Holding a different sidebar destination must enter edit mode at that destination without the route-reset effect immediately clearing it. Remove old session storage and prevent old `?edit` shortcuts from restoring a persistent state.

**Inline creation and editing.** Titles become borderless text inputs only in edit mode, with the same typography as their reading view. Add creates an inline blank item, focuses its first field and persists edits automatically. No pencil button or modal for a title, tab, topic, note, story, direction or goal. Empty saved names use a safe internal fallback such as Untitled while presenting an editable placeholder. Necessary technical controls, file upload dialogs and confirmations remain compact and in context.

**Drag arrangement.** Provide shared sortable tabs/cards and editor block handles. Show handles on hover/focus in edit mode; support mouse, touch and keyboard pickup/move/drop, visible drop position and Escape cancellation. Remove up/down buttons. Persist stable IDs and order together; failed saves roll back the order visibly. Do not let dragging trigger the card's ordinary open action. Reuse this system for Learn topics/tabs, Interviews tabs, STAR stories and appropriate Direction items.

**Link normalization.** Add a shared `normalizeWebUrl()` boundary helper: trim input, add `https://` to bare domains/paths such as `example.com/jobs`, retain explicit valid HTTP/HTTPS URLs, and reject unsupported schemes or embedded credentials. Normalize on blur/save and through relevant server schemas so keyboard submission, pasted links and API writes agree. Apply to profile links, listings, careers links, inline hyperlinks and research links. Do not rewrite stored text generally or reinterpret a LeetCode handle as a domain. Keep meaningful error feedback for invalid input.

**Custom controls.** Build themed Select/Combobox and Date/Time controls once, then replace native dropdown/date/time controls throughout visible product forms. Use unstyled accessible primitives for menus/popovers, with project styling rather than browser UI. [Radix Select](https://www.radix-ui.com/primitives/docs/components/select) provides the needed keyboard interaction. Date controls must support direct typing, calendar navigation, clearing optional dates, and consistent date-only values; appointment controls must retain valid timezone conversion. File selection can still use the operating system's file dialog.

**Focus and scrolling.** Remove the current blue pointer-focus borders and automatic close-button focus ring after mouse actions. Use the existing ink treatment for keyboard-only `:focus-visible`, keeping keyboard location discernible without a blue halo. Preserve accessible dialog focus management. Hide internal scrollbar tracks without reserving their width (`scrollbar-width: none` plus WebKit scrollbar rules); retain wheel, touch and keyboard scrolling. Apply to application details, process strips, document panes and tab strips. Keep the site's main scrollbar. Do not remove scrolling or clip content to hide a scrollbar.

**Arrow.** Replace text `↗` with one shared SVG arrow, preventing emoji presentation on mobile. Use it for signed-out and signed-in Work branding and audit other occurrences. Cycle smoothly through blue, pink, lime and aqua, with a small multicolour glow contained around the arrow. Expose the exact requested `arrow-colour-change-page` parameter as the duration in seconds per colour, initially 3 seconds; use a single bounded positive configuration value for both brand instances. The spelling appears to mean pace: retain the user's spelling as an alias if a clearer internal constant is used. Honour the operating system's reduced-motion preference automatically even though the Settings toggle is removed.

Affected foundation: `src/components/ui.tsx`, `src/styles.css`, `src/app/App.tsx`, `src/app/identity.css`, `src/app/EditNavigation.tsx`, `src/lib/edit-mode.tsx`, and shared URL/schema helpers.

## 2. Shared freeform workspace for Learn and Interviews

Implement one self-hosted rich editor using Tiptap/ProseMirror's open-source core. Its document can be stored as structured JSON; see [persistence](https://tiptap.dev/docs/editor/core-concepts/persistence). This is a proposed implementation choice, not a dependency already installed. Paid editor services and collaborative hosting are unnecessary for this scope.

Initial capability must include paragraphs, headings, bold/italic/underline, nested bulleted and numbered lists, task lists, indentation, hyperlinks, code blocks with a language selector, quotes, dividers, simple tables, undo/redo, paste cleanup and drag arrangement. A slash menu and a small selection toolbar provide formatting without permanent panels. Use a shared block handle implementation or the documented [Tiptap drag handle](https://tiptap.dev/docs/editor/extensions/functionality/drag-handle) after checking the chosen extension's license. Read mode renders the same document without editing controls. External links open normally in view mode and remain editable in edit mode.

Persist versioned editor JSON in owner-scoped content records and derive plain text for record search. Validate supported node types, links and document size server-side; render through the editor schema rather than arbitrary stored HTML. Debounce saves around 800 ms, save after meaningful changes, and retain an owner-specific local draft immediately. Show understated Saving/Saved/Retry/conflict states. Navigation may end editing while the pending save finishes; preserve an unsaved draft if that save fails. A stale response must never replace newer typing. Flush on blur when possible and recover drafts after reload. Preserve separate server versions and require conflict review rather than silently overwriting another session.

Replace `ContentPanel`/`AutosaveNote` presentation with this document model. Migrate existing main text, note titles/bodies and resources into one ordered document per topic/tab; resource URLs become link blocks. Preserve existing Markdown, ordering, owner/context IDs and original records in recoverable history/backups. Remove descriptions and technology-picker controls from new UI; fold authored old descriptions into body text during migration instead of discarding them. Version the rich-content format and handle old backups explicitly. Future resources can be plain links, inline links or compact link blocks within the document, without a separate Resources & notes system.

## 5. Applications: one process and status model

**Model:** every new application has fixed **Application → Offer** endpoints. Users can insert/reorder named assessment/interview/other steps between them. Only Planned and Completed are editable step states; the first planned step is the derived active step. Status selection contains Applied, the application's custom intermediate step names, Offer, Accepted and Rejected. Intermediate status options use yellow, retaining stable step IDs even when their labels change. Store the selected step ID separately from its title and terminal outcome; display one combined status control rather than contradictory broad/current controls.

Define transitions in shared domain code before building the UI:

- Applied completes Application; remaining steps are planned.
- Selecting an intermediate step completes preceding steps and leaves the selected step planned/active. Its later planned peers retain plain borders.
- Completing an intermediate step advances to the next planned step; moving backwards explicitly restores later steps to planned. Do not silently overwrite a terminal outcome during editing.
- Offer means the offer has been received; preceding process steps and Offer are completed. Accepted keeps that completion and records the terminal outcome. Rejected retains the actual reached/completed steps and records a terminal outcome without inventing completion of later steps.
- Scheduling or passing an appointment time does not automatically mark a recruitment round completed. Step completion is an explicit user action.

Keep completion as a contiguous process prefix in the normal editor so the derived first planned step and displayed status agree. No editable Current, Cancelled, Skipped or milestone-date fields. Archived legacy states remain historical data, not new options. Update validators, record contracts, filters, timeline consumers, exports/restores and demo fixtures together. Existing Saved/Withdrawn and ambiguous In progress records retain their true legacy history until explicitly updated; never relabel a never-submitted application Applied or a withdrawal Rejected. Use a compact read-only legacy label where migration cannot infer the new state. Preserve skipped/cancelled/dated history in a legacy snapshot rather than silently marking those steps completed.

**Process UI:** show an inline editable process strip in the existing application detail. No separate process submenu, dashed cards, Schedule control within a step, milestone date picker or appointment hyperlink. Completed steps have thin green borders all around. The first planned step has the existing blue raised treatment; later planned steps have normal black borders. If an appointment exists, show its date/time as plain text on that step.

**Scheduling UI:** rename Schedule interview to **Schedule** and use a small inline form in application details with required Step, Title and Date/time. The step picker shows this application's existing steps and cannot accept a removed/foreign step. If there is no eligible step, prompt inline to add one first. Hide timezone, status, meeting URL and source URL fields; interpret entered times in the user's Settings timezone, store a canonical instant, and handle daylight-saving ambiguity correctly. Email/meeting links belong in application notes. Preserve existing appointment states and extra fields in historical data without displaying them as new scheduling inputs.

**List and radar:** make only the hovered listing link blue; role text remains ink and whole-row opening stays intact. Remove the step sublabel beneath Status. Clamp notes with an ellipsis and use fixed table-column widths/row sizing so long text cannot stretch the listing; full notes remain in detail. Radar creation has Company, Careers page and inline notes, with no Website or Why it interests you field and no extra notes subheading. Preserve legacy values as readable notes/backup metadata.

**Remove preparation coupling:** no Prepare link, appointment-to-preparation navigation or generated per-appointment prep tabs. Appointments remain linked to their application/process step and Home timeline. Interviews retains a compact upcoming appointments overview showing only company, appointment title and time; it opens application details if selected. Existing round-specific prep content migrates into ordinary user tabs so removing this relationship does not lose notes.

Primary files: `shared/applications.ts`, `ApplicationsPage.tsx`, `InterviewEditor.tsx`, `applicationRecords.ts`, application styles, server contracts, references and backup remapping.

## 9. Replace the Docker/Colima compiler with the Pi service

Deploy a separate native compiler service under `/home/manav/base/work_project`, running directly on the Pi. Work's Cloudflare Worker remains responsible for user authentication, ownership, revisions and durable job records. The Pi receives only the selected project's source files and returns actual TeX-generated PDF/log/text/font/SyncTeX outputs. No Overleaf integration returns.

1. Inventory existing Pi services and tunnel routing without exposing their secrets. Confirm available storage/package footprint before installation. Install the required native TeX Live engines/packages, `latexmk`, `pdftotext` and `pdffonts`, plus a supported service Node runtime. The existing Node 20 must not be replaced globally if other Pi services depend on it; install the service runtime separately. Record engine/package/font versions and stop claiming a Docker image digest is the compiler fingerprint.
2. Replace `compiler/server.mjs`'s Docker launcher with a native per-job runner. Keep file/path/size validation, no shell escape, no source `latexmkrc`, bounded logs/artifacts, cancellation and job cleanup. Use an unprivileged dedicated service account, private temporary workspaces and a verified systemd/bubblewrap isolation design that denies network access and access to other home/services/secrets. Timeouts alone are not filesystem isolation; prove the native runner cannot read a sentinel outside its permitted workspace. The controller may request narrowly defined job services, not arbitrary privileged commands.
3. Install separate systemd units for the compiler controller/job runner, with startup, restart, log limits, private service environment and health checking. Start with one simultaneous compile on this 4 GB Pi; measure representative compile time/memory. Pi outages and capacity produce a clear retryable state in Work without losing source.
4. Reuse the existing `cloudflared` service and add one compiler hostname routed to the loopback controller. Preserve every existing tunnel route/service. Cloudflare Tunnel maps a hostname to a local service; see [routing](https://developers.cloudflare.com/tunnel/concepts/routing/).
5. Protect that hostname with Cloudflare Access service authentication. Generate a dedicated service token and pass `CF-Access-Client-Id` / `CF-Access-Client-Secret` from Worker secrets; keep the existing independent compiler bearer token at the service. See [service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/). Configure `LATEX_COMPILER_URL`, `LATEX_COMPILER_TOKEN` and dedicated Access credentials only in private server environments. No credentials or direct compiler requests go to the browser.
6. Prefer Pi-side queued jobs with authenticated status/artifact retrieval, rather than a long compile inside a Work Worker background task. Submit once, poll bounded requests through Work, and reconcile jobs interrupted by Pi/Worker restart. Artifacts remain temporary on the Pi until Work stores/verifies them; cap retention and clean expired jobs. Adapt compile cancellation and caching to the service's version fingerprint. This removes dependence on the current short synchronous compile deadline on a slower Pi.
7. Run one real representative résumé/cover-letter project through Work → tunnel → Pi → private storage → PDF preview/download. Verify extracted text, font embedding, errors and exact submitted revision association. Test unavailable Pi and cancellation once. Record native package versions and timing; no ATS compatibility guarantee is implied solely by using LaTeX.
8. Remove the compiler Dockerfile/container launcher and active Colima/VM setup instructions once the Pi path is verified. Clean up only Work-specific local VM/image/container artifacts after identifying them; uninstall developer-installed Docker/Colima tooling only if no unrelated project uses it. This planning turn performs no host cleanup. Update setup/operations docs, `.dev.vars.example`, deployment checks and compiler tests to the native service contract.

The compiler hostname and Access policy are configuration decisions at deployment time; use the existing domain/tunnel after inventory rather than creating a replacement tunnel. No new paid host is required by this architecture.

## Planning assumptions to retain during implementation

- The ambiguous upcoming-interviews wording means a compact shared appointments overview remains, while appointment-specific preparation tabs and links are removed.
- `arrow-colour-change-page` controls colour-change pace, not different colours for different pages.
- Removing an exposed field does not authorize discarding authored historical data. Legacy metadata stays in backup/history or is converted into readable body content.
- Hidden internal scrollbars remain scrollable; blue focus decorations are removed while ink keyboard focus remains usable.
- Technical custom pickers, link formatting popovers and rare conflict/deletion confirmation UI are compatible with eliminating unnecessary content-editor popups.
- The requested Notion-like experience includes capable local editing, not multi-user real-time collaboration, database views or a new external Notion connection.
